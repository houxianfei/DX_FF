# 傅里叶滤波器应用场景与集成指南

面向 Windows x64 / VS2019 v142 / C++17 集成开发人员，以当前工作区 SDK 1.0.1 为准（尚未正式发布）。本文按业务任务组织；方法参数见[接口参考](接口参考.md)，类型见[数据结构参考](数据结构参考.md)。

## 阅读入口与职责

| 任务 | 阅读位置 | 主要 API |
| --- | --- | --- |
| 连接与初始化 | 场景一、二 | `open`、`machine_info`、`initialize` |
| 单杆调试与异步控制 | 场景三 | `move_rod`、`send_rod`、`refresh_rod` |
| 配方保存与切换 | 场景四 | `record_positions`、`load_positions`、`send_partial_rods` |
| FF、stage、TDI 联动训练 | [Training 完整流程](Training计算流程.md) | 采样、寻谷、分配、执行 |
| 历史训练复用 | 场景五 | `load_training_archive`、重新分配和校验 |
| 停止与故障恢复 | 场景六 | `stop`、`emergency_stop`、`reset_faults`、`close` |

FF SDK 负责杆运动、反馈、校验、训练计算和文件读写。调用方负责流程编排、stage 运动、TDI 配置与成像、能量计算和图像保存。当前 GUI 的 Real 相机采集未接入，真实联动由集成应用实现。

下面片段位于集成应用的业务函数中，`driver` 是同一个 `FF::ff_driver`。每次失败立即保存本次 `code/message`，进入场景六的清理流程。完整可编译示例见[仿真示例](仿真示例.md)。

## 场景一：选择通道并连接

**前提**：部署匹配 DLL 和运行库，机台配置包含启用通道的杆、标定、层归属、邻接和间隙规则。真实模式需为各启用通道提供不同的有效串口，详见[安全边界及部署](安全边界及部署说明.md)。

1. 选择 Simulation 或 Hardware，先用 Simulation 验证软件流程。
2. 明确启用物理通道；GUI CH1/2/3 对应 API 的 0/1/2，Rod ID 不是数组下标。
3. `open()` 后刷新反馈，检查连接、位置及报警；读取配置摘要。

```cpp
FF::ff_driver driver;
FF::ChannelSelection enabled{true, false, true}; // CH1 + CH3
auto opened = driver.open("ff_config.json", FF::Mode::Simulation, {}, enabled);
if (!opened) { /* 保存 opened.code/message，清理 */ return; }
auto refreshed = driver.refresh();
if (!refreshed) { /* 清理 */ return; }
const auto info = driver.machine_info();
// 按 info.enabledChannels[ch] 遍历；不要以 ch < info.activeChannels 遍历物理通道。
// Hardware 时改用 FF::Mode::Hardware，并传 {"COM3", "", "COM5"}。
```

**成功判据**：所选通道连接正常、所需杆反馈有效且无报警。`open()` 不运动，也不表示已初始化。旧 `activeChannels` 重载只选择从 CH1 开始的前 N 个通道。

**GUI 对应**：Welcome / Connection Center → 选择模式、通道、配置及串口 → Open。失败时修正具体配置或连接问题。

## 场景二：首次建立 slot0 与初始化

**用途**：slot0 是经机台确认的初始杆位配方。绝对式电机无需运动寻零；`initialize()` 会实际运动到 slot0。

1. 首次建立 slot0：连接、读取实际位置，按经过验证的机械调试步骤手动调整各杆。初始化前允许手动运动和记录位置。
2. 整机就绪、反馈和实际布局确认后，记录全部启用杆位置为 slot0。
3. 正常开机调用 `initialize()`，成功后检查初始化标志，再开始 Training。

```cpp
// 只在首次调试确认后执行；不要每次开机覆盖 slot0。
auto recorded = driver.record_positions("slot_0.json", "commissioned initial positions");
if (!recorded) { /* 清理 */ return; }
// 正常开机从这里开始。
auto initialized = driver.initialize("slot_0.json");
if (!initialized || !driver.m_status.initialized) { /* 中止训练 */ return; }
```

**成功判据**：全部启用杆到位稳定，初始化标志为真。缺通道、缺杆、身份不符、报警或运动失败均应中止。失败时杆可能已有运动，应先检查实际反馈。

**GUI 对应**：手动建立初始位置 → 保存 Slot 0；每次 Open 后 Initialize。GUI 扫描与训练执行要求本次连接已初始化；SDK 集成应用也应主动检查此标志，不依赖所有运动 API 自动拦截未初始化操作。

## 场景三：单杆调试与异步控制

**前提**：确认地址、限位与标定。`mm = P0 + P1 × encoder`，P1 可为负。毫米目标转换、取整后还需重新校验。

1. `refresh_rod(address)` 后检查有效位置和报警。
2. 使用 `move_rod()`，成功表示实际位置进入容差且保持配置的稳定时间。
3. 需要保持应用响应时用 `send_rod()`，由同一控制线程轮询反馈，检查实际位置、容差、连续稳定时间、报警和超时。

```cpp
FF::Address address{0, 0}; // 替换为机台已配置地址
auto read = driver.refresh_rod(address);
if (!read) { /* 清理 */ return; }
// encoderTarget 由调用方按标定、取整和范围检查生成。
auto moved = driver.move_rod(address, encoderTarget);
if (!moved) { /* 保存错误并检查实际位置 */ return; }
```

**成功判据**：实际位置到位稳定。下发成功、硬件目标值或 `state == "Ready"` 本身均不能代替到位验证。

**GUI 对应**：Main UI 对应 CH 的位置编辑与发送。单杆运动不会自动先移动到安全位。同一 SDK 对象操作须串行，状态回调不得重入；快照读取不触发 I/O。

## 场景四：保存与切换位置配方

**前提**：配方属于当前机台/配置，文件包含的启用通道必须各自完整。新保存为 `FF-POS-2`，详见[位置文件格式](位置文件格式.md)。

1. 已到位的实际位置用 `record_positions()` 保存；编辑后的目标用 `save_positions()` 保存，后者不运动。
2. 切换时 `load_positions()`，检查结果及 `ignoredChannels`。
3. 普通配方允许缺少整个通道。用 `send_partial_rods()` 只下发文件包含的目标，再轮询至稳定；缺失通道不接收命令。
4. 若目标确实覆盖全部启用杆，可用阻塞 `move_rods()`；稀疏目标不得直接传给要求完整集合的多杆方法。

```cpp
auto loaded = driver.load_positions("recipe.json");
if (!loaded) { /* 保存 loaded.result，清理 */ return; }
if (loaded.value.targets.empty()) { /* 无适用目标，不发送 */ return; }
auto sent = driver.send_partial_rods(loaded.value.targets);
if (!sent) { /* 可能部分下发，检查实际反馈 */ return; }
// 控制循环 refresh()，按地址核对这些 targets 的实际位置、报警、稳定时间和超时。
// 全部稳定后才向上层报告切换完成。
```

**成功判据**：发送的所有杆稳定到位，未覆盖通道不接收命令。加载和保存本身不执行切换。slot0 初始化始终要求全部启用杆完整。

**GUI 对应**：Main UI Control 的 Slot 保存、加载作用于全部启用通道，不随 CH tab 缩小范围。

## 场景五：训练与历史结果复用

首次训练按[Training 完整流程](Training计算流程.md)采集、寻谷、编辑、分配、执行和验证。

| 目的 | 操作步骤 | 成功判据 |
| --- | --- | --- |
| 分析历史曲线并重新生成目标 | 加载 archive → 核对身份/通道/完整性 → 编辑候选或寻谷 → 当前设备初始化/刷新 → 重新分配与校验 → 执行 | 基于当前反馈重新规划到位，没有直接提交旧目标 |
| 恢复已验收杆位 | 加载另存的位置配方 → 按场景四切换 | 身份匹配，实际位置稳定到位 |

```cpp
auto archive = driver.load_training_archive("training.json");
if (!archive) { /* 保存 archive.result */ return; }
if (archive.value.machineId != driver.m_config.machineId ||
    archive.value.configVersion != driver.m_config.configVersion) {
  /* 仅查看数据，不执行；适配当前机台后重新训练。 */ return;
}
// 按当前 enabledChannels 逐槽取 channels[ch]，不自动启用旧文件中的通道。
// 清除调用方旧执行计划，按当前反馈重新分配与校验。
```

**GUI 对应**：Load Session → 检查曲线与候选 → Plan → Execute。加载清除旧计划；Save Session 自动保存到 `%PROGRAMDATA%\RSIC\FF\training_sessions` 并显示路径。保存会话不等于效果验收合格。

## 场景六：停止、故障恢复与关闭

| 触发情况 | 调用方操作 | 恢复条件 |
| --- | --- | --- |
| Stop / Stop Scan | 停止新采样，禁止新触发；取消 stage/TDI 采集；FF `stop()`；分别检查实际停止状态 | 保留部分样本为未完成，重新检查设备并初始化后新建扫描 |
| 紧急情况 | 使用机台硬件急停；软件侧请求外部设备急停/取消及 FF `emergency_stop()` | 排除原因并按机台流程解除急停，不自动续扫 |
| 报警、通信异常、超时或坏帧 | 保留首个错误和后续清理错误，停止新动作，清理全部参与设备 | 确认实际状态，按需 `reset_faults()` 后刷新并重新初始化 |
| 正常退出 | 结束业务，禁止触发，关闭 TDI/stage，再 FF `close()` | 逐个检查关闭结果；失败不宣称已断开 |

`stop()`、`emergency_stop()`、`reset_faults()` 和断开会清除初始化标志。复位成功不等于 Ready；刷新、检查报警/位置/安全状态后重新 `initialize(slot0)`。FF 停止 API 不会停止 stage 或 TDI，外部适配层必须分别处理。

GUI Stop Scan 保留部分样本。软件停止/急停不能替代独立硬件急停；连续轨迹安全按[安全边界](安全边界及部署说明.md)单独确认。
